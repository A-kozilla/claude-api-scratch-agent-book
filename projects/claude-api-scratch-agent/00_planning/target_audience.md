# ターゲット分析

## プライマリターゲット

### ペルソナ
- 年齢層・職業: 20代後半〜40代、Webエンジニア・SIer勤務のプログラマー・社内ツール開発者、社内でAI活用を推進する技術担当者
- スキルレベル: Pythonで小さなスクリプトやWeb APIクライアントを書いた経験あり。LLMはチャットUIで使ったことがあるが、APIでアプリに組み込んだ経験は少ない／エージェント開発は未経験
- 現在の課題: LangChain などのフレームワークやSDKのサンプルを動かしてはみたが、中で何が起きているか分からず、思い通りに動かないときにデバッグできない。「エージェント」「ツール呼び出し」「マルチエージェント」という言葉は知っているが、仕組みを自分の言葉で説明できない
- このコンテンツで解決したいこと: 依存を最小限にした自前のコードでエージェントを作り、仕組みを根本から理解したい。社内システムに組み込める、挙動・コスト・安全性を自分で制御できるエージェントを作れるようになりたい

### 選ぶ理由
1. SDKやフレームワークを使わず、HTTPリクエスト1本から全部を自分で書くため、「中で何が起きているか」が完全に見える
2. 自作クライアント → 単一エージェント → マルチエージェントと、1つのコードベースを段階的に育てるので挫折しにくい
3. リトライ・ストリーミング・コンテキスト管理・コスト・安全性など、サンプルでは省略されがちな実務上の論点まで踏み込んでいる

## よくある誤解・つまずき

| 誤解・つまずき | 本コンテンツでの対処 |
|------------|----------------|
| 「AIエージェント＝賢いチャットボット」という誤解 | 冒頭で エージェント＝LLM＋ツール＋ループ と定義し、第5章で実際に while ループを書いて「ループがエージェントの本体」であることを体感させる |
| 「APIは会話を覚えている」という誤解（ステートレス性の理解不足） | 第3章で、毎回の履歴を自分で messages 配列に積み直す実装を通して、API がステートレスであることとコンテキストウィンドウの意味を明確にする |
| APIキーの扱い・課金設定・環境構築でつまずいて離脱する | 第2章を環境構築に充て、Console での利用上限設定、`.env` と `.gitignore`、uv の導入、curl での疎通確認を順に丁寧に扱う |
| 古い記事のコードをコピーして 400 エラーになる（`temperature` やprefill、旧ヘッダー等） | API バージョン（`anthropic-version: 2026-10-21`）と現行仕様に準拠したコードで統一し、エラーレスポンスの読み方を第3章で教える |
| 429・529 やタイムアウトで止まるエージェントを作ってしまう | 第4章で指数バックオフ＋`retry-after`対応のリトライと、ストリーミングを自前で実装する |
| ツールの結果の返し方を間違える（tool_result を分割して返す、エラーを握りつぶす） | 第5・6章で tool_use / tool_result の対応関係、1メッセージにまとめて返すルール、`is_error` を使ったエラー返却を具体例で示す |
| いきなりマルチエージェントを作ろうとして複雑さに挫折する／「マルチエージェントの方が常に優れている」という誤解 | 単一エージェントを先に完成させ、第9章で「単一呼び出し → ワークフロー → エージェント → マルチエージェント」の判断基準を示してから使い分ける |
| エージェントに「何でもできる」という過剰な期待を持つ | ハルシネーション・コスト・レイテンシ・プロンプトインジェクションなどの限界とリスクを明示し、第11章で評価・ガードレール・コスト管理の現実的な指針を示す |
